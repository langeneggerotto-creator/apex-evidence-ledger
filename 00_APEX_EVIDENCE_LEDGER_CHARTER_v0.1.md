## Purpose Kernel

**The APEX Evidence Ledger exists to ensure that no meaningful module claim, build status, validation result, promotion decision or rollback action outruns its recorded evidence.**

## Core Responsibilities

1. Maintain the APEX Repository and Module Registry.
2. Define public-safe claim, evidence, decision and validation record formats.
3. Preserve build receipts, hashes, status transitions and rollback records.
4. Define GitHub auto-capture rules for qualifying artifacts.
5. Enforce truth-status distinctions: `VERIFIED`, `INFERRED`, `PROPOSED`, `BLOCKED`, `ASPIRATIONAL`.
6. Maintain ECHO traceability: what changed, why, by whom/what process, on what evidence, and what happens next.

## Truth Boundary

This repository can define evidence structures and preserve public-safe evidence artifacts. It does not itself prove the operational truth of every downstream module until the required evidence records are created and independently validated.

## Evidence Promotion Gate

No APEX module should be presented as operational, validated, deployed or improved without:

- an identifiable artifact or measured outcome;
- a recorded truth status;
- a validation or review record;
- a version/commit reference;
- a limitation or unresolved-gap statement where applicable;
- a next control or proof gate.

## Public Repository Restriction

Do not commit employer data, personal data, credentials, private correspondence, protected datasets, internal SharePoint information or proprietary business material. Such material requires a controlled private repository or redacted evidence capsule.

## Final Direction Stack

1. Create the suite repository registry and evidence schemas.
2. Define automatic public-safe capture rules and promotion gates.
3. Connect the Mirror and Iteration Automater status feeds to evidence receipts.
4. Sandbox a visual Provenance Galaxy showing artifacts, claims, tests and dependencies.
